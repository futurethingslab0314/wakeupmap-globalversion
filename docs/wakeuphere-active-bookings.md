# WakeUpHere 同城市有效預約名單

更新日期：2026-11-21。

## 現行規則

每個帳號先取最新預約，再檢查是否有效及是否屬於查詢的城市／國家。順序不可顛倒，否則新預約已換城市或取消時，舊地點仍會找到歷史列。

有效預約需有非空白帳號、城市、有效勾選及明確的預約更新時間。它表示「仍保留的每日城市鬧鐘預約」，不表示設備目前在線；關機不會自動取消每日預約。

帳號比對沿用現有正規化方式：忽略大小寫、空白、底線與連字號。不要用這些差異區分不同使用者；此機制不是登入驗證。

## Notion 欄位與舊資料

API 首次建立／更新預約時，檢查並自動補上：

| 欄位 | 型別 | 用途 |
| --- | --- | --- |
| `wakeuphere_active` | Checkbox | 是否仍為有效預約 |
| `wakeuphere_updated_at` | Date | 預約設定／取消的伺服器時間 |

若缺少可用的英文國家文字欄位，且新預約有提供國家，另補 `setup_country` Rich text，以免同名城市混在一起。既有欄位若出現不相容型別，回報失敗，不覆寫欄位型別。

沿用原 Notion API `2022-06-28` 版本；新增欄位需要 integration 的 update content 權限。只增加缺少欄位，不刪欄位／歷史列。沒有這兩個預約狀態值的舊紀錄，不直接推定為有效；設備載入新版並成功同步後才會重新顯示。

最新紀錄依專用 `wakeuphere_updated_at` 比較；只有歷史列尚未有專用時間時，才用 Notion `last_edited_time`／`created_time` 選擇可升級的列。已有專用預約時間的紀錄優先於沒有狀態的歷史列，避免一般編輯歷史內容導致復活。

同一帳號後續預約會更新該帳號最新列，包括新城市／國家與有效狀態；其他歷史列不刪除。取消將最新列標為無效，保留其城市作為操作比對資料，不會回頭選另一筆舊有效列。

## API 與前端同步

POST 支援：

- `reserve`：確認／恢復預約，設定最新城市並標為有效。
- `cancel`：取消相符地點的預約、標為無效。
- `dismiss`：記錄停止響鈴，保留每日預約，不更動預約更新時間。

取消與停止訊號會核對最新預約的地點；若來自舊地點，回傳 `ignored`，避免把新地點撤銷或改回舊地點。舊前端未提供 action 時仍相容：press=yes 視為 dismiss，其他視為 reserve。

前端以持久 FIFO 佇列序列化寫入，payload 在操作當下擷取，避免選址變更後誤用新城市。確認後先完成寫入再讀取同城名單。重新選址確認為「是」時，先排入取消，再清除本機排程；改 userName 時也會先取消舊身份的該地點。

名單每 60 秒刷新，包含城市與國家條件，GET 使用 no-store。快速換城市或重選時，過期的非同步回應不會覆蓋目前名單。

斷網或 API 失敗時：變更保存在 `localStorage` 的 `wakeuphere.bookingOutbox`，畫面顯示同步未完成；每 15 秒及網路恢復時重試。重開頁面也會先還原待送變更。只有成功寫入遠端後，其他設備才會看見取消或新預約；不宣稱斷網能即時更改遠端資料。清除瀏覽器網站資料會失去尚未送出的佇列。

新增預約／重開頁面同步與其他同帳號設備操作若同時發生，遠端以最後完成的預約寫入為準；每個人應使用自己的帳號名稱。Notion 不提供此流程的跨請求交易鎖，這不是多設備協作編輯或即時在線狀態服務。

## 驗證與部署

```bash
npm run test:wakeuphere-bookings
npm run test:wakeuphere-alarm
npm run test:wakeuphere-update
npm run lint
npm run build
```

測試以假的 Notion API 回應驗證新增狀態欄位、分頁、最新紀錄去重、換城市、取消、不讓歷史列復活、同名城市國家區分、停止響鈴保留預約、舊地點操作保護、寫入先後、斷網重試與過期回應。

部署後，各台 Pi 透過現有版本檢查載入新版即可，不需重裝硬體控制。舊帳號若仍有預約，需載入新版並同步成功後才會出現在名單。若持續顯示同步未完成，查 Vercel API 記錄及 Notion integration 的資料庫編輯權限。

參考：[Notion 舊版 API 新增資料庫欄位](https://developers.notion.com/reference/update-property-schema-object)。
